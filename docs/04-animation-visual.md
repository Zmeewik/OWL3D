# Animation & Visual Systems

## Two parallel animation stacks

The project has **two separate, non-overlapping animation systems** for two different purposes:

### 1. Generic entity animation (`EntityAnimator` + `EntityAnimationManager`)

Used for non-player entities (enemies). `EntityAnimator` is a `MonoBehaviour` holding a `sharedAnimator` (full-body) plus a list of named per-body-part `Animator`s (`BodyPart { name, animator }`), a hardcoded `animationList` of known animation names (`melee_attack`, `hit_front`, `block_start`, `idle`, ...), a play-queue (`Queue<(anim, part, loop, speed)>`), and per-key loop-coroutine tracking (`Dictionary<string, Coroutine>`). `EntityAnimationManager` is a thin singleton facade (`Play`/`Enqueue`/`StopAllAnimations`) that forwards to whichever `EntityAnimator` instance is passed in — it inherits `IAnimation` (abstract base: `Play`/`Enqueue`/`StopAllAnimations`) but is otherwise stateless itself. `EntityAnimator.Awake()` subscribes to its own `EntityHealth.OnAnimateCommand` to auto-play a random hit-reaction animation on damage (`GetHitAndReturn` — stops all loops, plays a random `hit_*` clip, then enqueues a random `idle` clip after).

### 2. Player-specific animation (`HeroAnimationController` + `WeaponAnimationController` + `EntityAttackAnimation`)

This is the system actually driving the first-person view. It does **not** reuse `EntityAnimator`/`IAnimation`'s queue machinery even though `HeroAnimationController` and `WeaponAnimationController` both also inherit the same abstract `IAnimation` base — each reimplements its own separate queue/loop bookkeeping (`Queue<QueuedAnim>`, `PartQueueData`, `PlayNextInQueue`/`WaitThenNext` coroutines) independently, near-identically, three times over (once per class). This is the same "shared abstraction exists but isn't shared" pattern as the melee/ranged weapon classes.

- **`HeroAnimationController`** (singleton) — owns 4 arm/leg `Animator`s (`left_hand`, `right_hand`, `right_leg`, `left_leg`). Its `AnimationState` enum is a **hand-authored, fully-spelled-out list of every clip name** used across all three weapon types (Boxing/Pistol/Kunai) — e.g. `H_Arms_Boxing_HitChargeStart1`, `H_Arms_Pistol_Reload`, `H_Arms_Kunai_Throw3`, plus shared parkour clips `H_Arms_GetUp`/`H_Arms_ClimbUp`. A **parallel `string[] animationNames` array must be kept in the exact same order as the enum** (`animationNames[(int)state]`) — there is no `[Description]`/`nameof` link between them, so inserting a value in the middle of one without the other silently desyncs every subsequent animation. Subscribes directly to `PlayerMovement.OnPlayAnimationLArm/RArm/RLeg` (a *third* animation-command channel, separate from `IAnimateCommand` and `IAnimationSender`).
- **`WeaponAnimationController`** — one instance per equipped weapon's arm-model, drives a single `Animator`. Its `ChangeAnimationName` does **runtime string surgery** on incoming animation names: strips `"_Arms"`, appends `"_Bake"`, and replaces the embedded weapon-name token if it doesn't match this instance's own `weaponName` (e.g. an incoming `"H_Boxing_Idle"` becomes `"H_Pistol_Idle_Bake"` when played on the Pistol's controller) — so **one shared animation-name vocabulary is remapped per weapon via string manipulation** rather than each weapon defining its own clip name table.
- **`EntityAttackAnimation`** — the actual dispatcher: subscribes to `IAnimationSender.OnAnimateCommand` from a configured list of `animationSenders` (weapons + player), looks up the command in its own **third, separately-declared** `animationList` (same shape as `EntityAnimator`'s, but a different instance with `bodyPartsIntended`/`weaponIntended` index arrays), and fans the command out to whichever body-part/weapon controllers are indexed for that animation. Synchronizes `_start`/`_continue`/`_end` triplets by picking one random variant index at `_start` and reusing it through `_continue`/`_end` (`animationIndexes` dictionary keyed by animation name) so e.g. a charge-up and its matching charge-release use the same numbered clip variant.

**Net effect:** there are (at least) three independently-maintained lists of animation-name strings that all have to agree (`HeroAnimationController.animationNames`, `EntityAttackAnimation.animationList`, `EntityAnimator.animationList`), on top of the command-name strings from [01-architecture.md](01-architecture.md). This is the most fragile part of the codebase to extend safely — adding a new weapon animation means touching at least 3 files' string tables by hand with no compiler assistance.

## Particles (`Particles.cs`, singleton)

A named-lookup particle-effect service: `List<ParticleEffect>` (`name`, `type: InFront | InPlace`, prefab). `InFront` effects are pre-instantiated once at `Start()` as children of a `face` transform (e.g. muzzle flash, movement-speed-lines — always-present, just toggled active/inactive + `Play()`/`Pause()` on their child `ParticleSystem`s). `InPlace` effects are instantiated fresh at a world position on every call (e.g. `"MetalHit"` bullet-impact sparks) and self-destruct after their longest child system's `duration`. `ChangeColor(name, Color[])` pokes `startColor` on each child `ParticleSystem` positionally by index — colors are matched to child particle systems by array order, not by name.

Called from combat code as `Particles.Instance.StartEffect("MetalHit", hit.point, rotation)` and from `PlayerMovement.FixedUpdate` as `particles.ChangeColor("MovementLines", ...)`/`StartEffect("MovementLines")`/`StopEffect("MovementLines")` to drive the speed-lines effect's alpha directly from current momentum.

## Misc visual/animation stubs

- **`EntityBaseAnimation.cs`**, **`EntityBodyPartControl.cs`** — both completely empty `MonoBehaviour` classes (no fields, no methods). Present under `Entities/Behaviour/ProceduralAnimations/` but unused; likely scaffolding for a planned procedural-animation system (IK foot placement, look-at, etc.) that was never started.
- **`AnimationHide.cs`** — trivial helper, toggles a list of `MeshRenderer`s' `enabled` flag on/off (used to hide/show a weapon's mesh independent of its animation state).
- **`DebugHPBar.cs`** — runtime-generated (no prefab) world-space health bar: builds a `Canvas`+`Image` fill bar + legacy `Text` label entirely via `new GameObject()`/`AddComponent` in `Awake()`, subscribes to `EntityHealth.OnTakeDamage`/`OnDeath`, billboards toward `Camera.main` in `LateUpdate`. Clearly a debug/placeholder UI, not the shipping HUD.
